# BE FABULOUS: контракт публикации прайса

Этот документ предназначен для проекта административного приложения. Его задача - сформировать и опубликовать актуальный прайс для статичного клиентского сайта BE FABULOUS.

## Результат публикации

Административное приложение должно коммитить ровно один JSON-файл в репозиторий клиентского сайта:

```text
public/data/services.json
```

После деплоя статичный сайт загружает его по относительному URL:

```text
public/data/services.json
```

Это относительный, а не доменный URL. Поэтому он работает как на собственном домене, так и на GitHub Pages, развёрнутом в подкаталоге репозитория.

Примеры итогового URL:

```text
https://example.com/public/data/services.json
https://username.github.io/repository-name/public/data/services.json
```

Не нужно публиковать файл в отдельный API, Cloudflare Worker или raw.githubusercontent.com: сайт и JSON должны быть опубликованы вместе и доступны с одного origin.

## Схема JSON

Файл должен быть валидным UTF-8 JSON без комментариев и без завершающих запятых.

```json
{
  "repairServices": [
    {
      "title": "Брюки и джинсы",
      "items": [
        {
          "name": "Подшить брюки",
          "price": "от 800 ₺"
        }
      ]
    }
  ],
  "sewingServices": [
    {
      "name": "Топ / корсет",
      "price": "от 4 000 ₺"
    }
  ],
  "includedItems": [
    "Консультация и обсуждение модели",
    "Снятие мерок"
  ],
  "excludedItems": [
    "Основная ткань",
    "Фурнитура"
  ],
  "extras": [
    {
      "name": "Срочный заказ",
      "price": "+30%"
    }
  ]
}
```

### Поля и правила

| Поле | Тип | Обязательность | Использование на сайте |
| --- | --- | --- | --- |
| `repairServices` | массив групп | Да, если нет `sewingServices` | Блок «Ремонт и подгонка» на `price.html`; услуги попадают в select формы. |
| `repairServices[].title` | непустая строка | Да для каждой группы | Заголовок группы ремонта. |
| `repairServices[].items` | массив услуг | Да для каждой группы | Строки прайса и варианты select. |
| `repairServices[].items[].name` | непустая строка | Да | Название услуги; передаётся в заявке как поле `service`. |
| `repairServices[].items[].price` | непустая строка | Да | Отображаемая стоимость услуги. |
| `sewingServices` | массив услуг | Да, если нет `repairServices` | Блок «Индивидуальный пошив»; услуги попадают в select формы. |
| `sewingServices[].name` | непустая строка | Да | Название услуги; передаётся в заявке как поле `service`. |
| `sewingServices[].price` | непустая строка | Да | Отображаемая стоимость услуги. |
| `includedItems` | массив непустых строк | Нет | Список того, что входит в пошив. |
| `excludedItems` | массив непустых строк | Нет | Список того, что не входит в стоимость. |
| `extras` | массив услуг | Нет | Блок дополнительных условий. |
| `extras[].name` | непустая строка | Да, если есть элемент `extras` | Название дополнительной услуги или условия. |
| `extras[].price` | непустая строка | Да, если есть элемент `extras` | Отображаемая цена или правило, например `+30%`. |

Как минимум одна услуга должна остаться после проверки: либо в `repairServices`, либо в `sewingServices`. Иначе клиентский сайт считает файл некорректным и показывает резервный прайс.

Все поля `price` являются строками для отображения. Допустимы `"от 800 ₺"`, `"+30%"`, `"по запросу"`. Фронтенд не вычисляет суммы и не сортирует цены. Если денежная цена содержит число, но не содержит знака валюты, клиент автоматически добавляет знак турецкой лиры `₺`; процентные значения и текстовые условия остаются без изменений.

## Что использует клиентский сайт

1. `price.html` строит весь прайс из файла.
2. Select выбора услуги на `index.html`, `price.html` и в текущей локальной `admin.html` строятся из объединения `repairServices[].items` и `sewingServices`.
3. Значение `name` выбранной услуги отправляется в Telegram Worker в поле заявки `service` без преобразования.
4. `includedItems`, `excludedItems` и `extras` не участвуют в выборе услуги и не отправляются в заявке.

Первым вариантом каждого select всегда остаётся `Консультация / уточнить услугу` с пустым значением. Если его оставили выбранным, в заявку уходит `Консультация`.

## Требования к административному приложению

- Редактор должен хранить и публиковать данные в объектной структуре, показанной выше. Поддержка массивов вида `["Название", "Цена"]` существует в клиенте только для обратной совместимости; их использовать не нужно.
- Перед публикацией нужно проверять обязательные строки на пустоту после `trim()`.
- Названия услуг рекомендуется делать уникальными во всём файле: `name` является идентификатором, который видит пользователь и который сохраняется в заявке.
- Сохраняйте цену с уже готовой локализацией и валютой. Рекомендуемый формат: `от 1 200 ₺`.
- Не добавляйте HTML в строки. Сайт экранирует вывод, поэтому HTML будет показан текстом.
- Не добавляйте произвольные поля как способ повлиять на сайт: неизвестные поля будут проигнорированы. При необходимости новой функциональности контракт нужно расширять отдельным изменением фронтенда.
- Сохраняйте разумный порядок элементов: фронтенд показывает массивы в том же порядке, в котором они записаны в JSON.

## Публикация в GitHub

Административное приложение должно создавать коммит в том же репозитории и в той ветке, из которой выполняется production-деплой сайта. Обычно это `main`, но ветку следует брать из конфигурации проекта, а не фиксировать в коде.

Допустимые реализации:

- GitHub Contents API: `PUT /repos/{owner}/{repo}/contents/public/data/services.json`.
- Git commit API или обычный `git commit` + `git push` от сервисной учётной записи.

Для обновления существующего файла через Contents API в запросе нужен текущий `sha` файла. Минимальное тело запроса:

```json
{
  "message": "chore: update services price list",
  "content": "<base64-encoded UTF-8 JSON>",
  "branch": "main",
  "sha": "<current-file-sha-on-update>"
}
```

Токен GitHub должен храниться только на серверной стороне админского приложения. Ему нужны права на запись содержимого целевого репозитория (`contents: write` для fine-grained token либо эквивалентные права классического токена). Никогда не передавайте этот токен в браузер администратора.

Перед коммитом следует заново получить текущий `sha` и повторить попытку при конфликте `409/422`: это предотвращает перезапись более свежего прайса, если файл одновременно редактируют в GitHub или другой экземпляр админки.

## Проверка перед публикацией

Админский сервер должен выполнить все пункты до обращения к GitHub:

1. Сериализовать объект в JSON.
2. Убедиться, что JSON разбирается стандартным парсером.
3. Убедиться, что есть хотя бы одна валидная услуга в `repairServices` или `sewingServices`.
4. Проверить непустые `title`, `name` и `price` для всех публикуемых элементов.
5. Проверить уникальность `name` среди услуг ремонта и пошива.
6. Публиковать файл атомарным коммитом: не оставлять в репозитории пустой, частичный или временный файл.

После успешного ответа GitHub админка может считать операцию принятой. Появление изменения на публичном сайте зависит от обычного времени деплоя GitHub Pages или Cloudflare.

## Совместимость с GitHub Pages и Cloudflare

Сейчас менять пути не нужно. Клиент использует относительный URL `public/data/services.json`, который корректен для:

- GitHub Pages на custom domain;
- GitHub Pages project site (`https://username.github.io/repository-name/...`);
- Cloudflare Pages;
- статической раздачи Cloudflare Worker, если файл включён в статические assets.

Важно сохранить в deploy-артефакте каталог `public/data/services.json` без переименования. Если в будущем production будет публиковать JSON по другому пути, например `/services.json`, нужно синхронно изменить константу `SERVICES_URL` в клиентском [script.js](script.js:4).

## Поведение при сбое

Клиент запрашивает файл при открытии страницы с `cache: "no-store"`. Если сервер вернул ошибку, JSON повреждён или в нём нет услуг, сайт не ломается: используется встроенный резервный прайс. На странице прайса дополнительно показывается предупреждение, что данные взяты из резервного списка.

Это означает, что ошибочная публикация не должна превращать страницу в пустую. Но резервный список не синхронизируется автоматически, поэтому админскому приложению нельзя рассматривать fallback как успешную публикацию.

## Вне области интеграции

Публикация `services.json` не отправляет заявки и не требует доступа к Telegram. Действующий Telegram Worker остаётся отдельной интеграцией фронтенда; его URL, токены и настройки не нужны проекту управления прайсом.
